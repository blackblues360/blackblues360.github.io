## 可重复的真实设备步骤

1. 本地与正式数据库版本、发布文件、回调白名单确认后，Windows 与真实手机分别登录 A；另一个独立浏览器登录 B。
2. 孔板创建一个包含不同板型、中文标签和颜色的方案。A 在 Windows 保存，手机打开并核对孔位/标签/颜色；手机修改后 Windows 重载核对。另存 JSON，比较 JSON 值并记录 revision。
3. SOP 创建操作/等待并行块、容器、环境标注和中文格式文本。双设备往返；导出 `.soptime` 后重新导入，核对时间、关联和文件兼容性。
4. 两端读取同一 revision。A 保存后，B 编辑旧版本提交必须冲突，B 内容保持可编辑且可导出。先另存独立副本，再明确确认重载云端。
5. 断开设备网络，编辑并保存必须失败；恢复网络不能自行覆盖。手动重试，遇到冲突仍保留本页内容。
6. A 软删除，正常列表消失；回收站恢复后 revision 递增。二次确认永久删除后，正文和名称清空、不能恢复、旧 ID 不能重建。
7. 切换到 B，不能列出、读取、更新、删除或恢复 A 的文档和 A 的本机未同步草稿。A 返回后草稿可恢复。
8. 检查真实邀请/重置链接不进入日志或截图；记录设备、浏览器版本、网络、时间和结果。此文只是方法，不能记作已执行。

## 网关与抗滥用的架构建议（尚未实施）

现有数据库限制继续有效：单文档 JSONB 文本 5,000,000 字节，每用户工具文档 1000 个、总正文 100 MiB，纪念日 1000 条，每分钟 120 次成功写入；均有实际 SQL 断言。永久清空正文释放内容容量，但保留 ID 名额，避免无限制造墓碑。错误顶层格式、app_id/schema_version 由数据库拒绝；完整编辑语义由工具校验。

数据库事务失败/回滚时，同事务内计数也回滚。因此成功写入计数不是失败请求限流，JSONB 长度约束也不是请求到达数据库前的字节限制。Auth 端点的限流不能代替业务 REST/RPC 限流。官方说明允许配置 Data API pre-request 检查，但这仍位于数据库请求处理过程，且仅覆盖 PostgREST，见 [Securing your API](https://supabase.com/docs/guides/api/securing-your-api)。本阶段没有通过这些检查证明“所有失败请求均被持久计数”。

建议另行审核可控后端入口：流式读取时限制字节数、验证 JWT、以账户/IP 独立计数失败请求、设置超时，并继续采用所有权与 CAS。必须同时撤销或限制客户端直连业务表/RPC 的写权限，后端凭据只留服务端，不能用仅修改前端 URL 的代理宣称堵住旁路。这会改变现有 GitHub Pages→Supabase 的信任与部署边界，需要单独设计和授权；本阶段没有擅自添加服务、升级套餐或改造生产权限。
