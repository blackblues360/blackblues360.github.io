# 阶段 B 运行与数据保护规则

本文件记录阶段 B 的规则与当时限制。阶段 C 的回收站、正式备份进展和发布阻断项见 [阶段 C 报告](stage-c-report.md)、[备份报告](stage-c-backup.md) 及 [发布验收清单](stage-c-release-checklist.md)。

## 环境与邀请制

正式项目 blackblues-account，组织 blackblues，ID `orjmbavlxuuccxdphepi`，新加坡 `ap-southeast-1`。管理 API 已核实组织套餐为 free；未购买插件、升级或变更 GitHub Pages。

公开配置只含项目 URL 和 Publishable Key。数据库密码是本机加密凭据，Service Role / SMTP 密码不得放入浏览器、GitHub、日志或报告。共享会话键 `blackblues.auth.v1`，每台设备独立登录。账号切换增加请求代数、取消待执行业务请求并清空旧账户内存；未同步草稿按用户 ID 隔离。

全局注册关闭、匿名登录关闭；邮箱提供商保持启用。不能把 email.enable_signup 也设为 false，否则连邮箱登录都会被禁用。本地测试实际遇到并修正了这个问题。只由管理员通过 Supabase 的受邀用户流程发邀请；前端没有开放注册入口。

正式 Site URL 仅 `https://blackblues.xyz/account/`，额外回调仅 `https://blackblues.xyz/account/callback/`。静态文件真实存在，不能依赖路由回退。邮件使用 token_hash；回调读取后立即清理地址栏，再验证邮箱并进入账户中心。不要把含令牌的链接放入日志、截图或第三方页面。

认证邮件域名 `auth.blackblues.xyz`，Resend Free，SMTP 接入已核实。发件地址应为 `noreply@auth.blackblues.xyz`。用户已报告域名 Verified。DNS 采用 Resend 实际生成的两条 CNAME 与 DKIM TXT，保持 DNS only；公钥不是服务端秘密。邀请、验证、重置模板已版本化，生产副本与本地模板应保持相同内容。

账户注销采用明确申请流程：账户中心导出数据后向既有站点联系邮箱申请，管理员核验邮箱控制权及本人意愿、说明不可恢复范围、保留必要备份后，由服务端管理员删除 Auth 用户并验证业务外键级联。不能仅凭来信自报 ID 删除账户；浏览器不持有删除账号的管理员权限。本阶段没有自动注销接口，也没有自动发送申请邮件。

## 容量与频率

| 项目 | 当前机制 | 边界 |
| --- | --- | --- |
| 单工具文档 | DB JSONB 文本最多 5,000,000 字节；顶层 v1 格式检查 | 不等于完整 JS 语义验证，也不等于原文件字节备份 |
| 请求体 | 前端纪念日预检 128 KiB，工具基础模块 7 MiB | 客户端预检可绕过；尚未验证托管网关的硬请求体上限 |
| 用户容量 | 工具文档最多 1000 个、JSONB 文本合计 100 MiB；纪念日最多 1000 条 | 含软删除；不代表数据库索引、Auth、WAL 等物理占用 |
| 写入频率 | 每用户每分钟 120 次成功写入，事务内计数与用户级锁 | 回滚/失败请求不计数，不能代替网关抗滥用限流 |
| 登录 | 配置每 IP 每 5 分钟 30 次登录/注册请求、30 次验证，150 次刷新 | 登录失败枚举/真实网络限流压力测试尚未执行 |
| 邮件 | 同一用户请求间隔 60 秒；全项目每小时 10 封 | CLI 不管理 email_sent，已通过管理 API 设置并读回核实；同时受 Resend 免费额度约束 |

这些数值用于个人邀请内测，避免一次操作或重试占满免费实例；并不授权公开注册。扩展内测人数前应评估免费项目总容量，不能将“每用户 100 MiB”理解为任意数量用户都可用。

超限或网络失败时保留表单和本地草稿，提供文件导出，不自动取得新 revision 后覆盖提交。满配额下同 ID 重试仍返回唯一键冲突，客户端读取自己同 ID 记录并核对内容；不同内容必须冲突。更新与删除均比较旧 revision，软删除保留 ID，旧请求不能复活。

阶段 C 前需要落实并实测网关硬请求体上限和失败请求限流。建议目标工具请求 7 MiB、纪念日 128 KiB；托管直连 PostgREST 若不能配置，应先评估可控服务端入口及禁止旁路的设计，单独审核后实施。本阶段没有用前端检查冒充网关限制。

## 备份与恢复

Supabase Free 应定期独立导出；不能依赖 Pro/Team 才提供的每日托管备份。见 [官方备份说明](https://supabase.com/docs/guides/platform/backups)。建议内测使用前及每次迁移前导出，开始使用重要数据后每日备份，保留 7 个日备、4 个周备、3 个时间点月备，至少一份放在加密的站外位置。尚未建立定时备份任务，不能据此承诺 RPO。

账户中心 JSON 导出是业务数据逻辑副本；不含 Auth 凭据、数据库权限、存储文件或原始 JSON 字节。数据库完整恢复还需匹配 PostgreSQL 版本、角色/扩展、Auth 数据与项目认证配置。Storage 对象必须单独备份，本阶段没有使用 Storage；数据库元数据备份不包含对象本体。

`scripts/backup-drill.py` 已在本地合成库演练：使用容器内同版本 pg_dump 生成完整归档，恢复到本次随机创建的独立数据库；核对业务日期/revision、RLS、表/列/函数权限、函数所有者和迁移历史，验证恢复后 authenticated RPC，最后只清理本次恢复库及合成身份。归档留在 `.local/backups`，不提交 Git。它不是跨云项目灾难恢复证明，也不复制对象存储。

首次普通 postgres 恢复失败于 Vault 权限；修正为容器内本地 supabase_admin 保留所有者恢复。默认 ACL 的空值与显式相同 ACL 按 PostgreSQL 的实际默认权限展开比较，列授权另行比较。不能为让测试通过而去除权限核对。

正式恢复演练尚未执行。重要数据开放前：用空的隔离目标环境恢复独立备份，核对 Auth 与业务所有权、RPC、软删除、数据数量/校验和及所需配置；实际记录耗时与可恢复时间点，再确定 RPO/RTO。不要在现有正式项目直接试恢复。

## 软删除与阶段 C 前置设计

纪念日和工具文档删除仅设置 deleted_at 并递增 revision；内测不自动物理清理。墓碑占配额；没有自动回收站恢复 RPC。管理员人工恢复必须先备份、验证所有者及用户意愿，通过独立受审操作递增 revision，并测试旧请求不能覆盖恢复结果。

阶段 C 前单独审核回收站列表、恢复时命名/容量冲突、永久删除确认与延迟策略、ID 墓碑保留策略、备份保留与注销的关系。当前不自动推进阶段 C，不接入孔板/SOP 云端管理。

## 日期与本地草稿

使用公历 DATE、设备本地日期；不按 UTC 时间戳除以 86400000 计算天数。2 月 29 日在非闰年按 2 月 28 日；年度重复不能早于原始日期首次发生。用户显示设置暂不跨设备同步。

孔板/SOP 在读取主草稿之前持有 Web Locks 排他锁；不能拿到锁或不支持锁时明确进入仅内存/文件模式。每次写入还核对主键快照，观察到外部变动即暂停。锁只约束遵循协议的页面；旧版本网站或其他脚本的非协作写入仍有边界。BFCache 恢复必须刷新才能重新取得写权限。

SOP 损坏草稿状态依然禁止写回；孔板无法恢复的原始文本同样保留并可下载。恢复失败且无可靠锁时，不会清除损坏文本；可能需要关闭占锁页面后刷新再恢复。所有用户原有浏览器数据均未被本次测试读取或删除，测试使用独立浏览器上下文。
